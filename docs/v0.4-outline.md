## 0. The target-hardware correction (decided during the pause)

SPEC §0.1 declares Apple Silicon the primary target. **The actual target is an
Intel MacBook Pro — i7, 16 GB RAM, dual GPU (Intel integrated + AMD discrete) —
and that is a mission statement, not a fallback:** the project's founding proof
is that this engine runs a show on the machine OBS could not serve. v0.4
revises §0.1 to name real hardware: Intel Mac with discrete graphics as the
reference target, Apple Silicon welcome but not assumed.

Consequences already pinned:

- `docs/hardware-baseline.txt` ([RI-2]'s probe) **is** the reference envelope.
  The resource model is arithmetic against that machine, not against an
  imagined one.
- The §12.6 unified-memory clamp stays dormant (no caller, and its machine is
  not this one) — but the resource contract v0.4 writes must speak **both**
  memory models: dedicated VRAM budgets on discrete GPUs, unified-memory
  clamping on Apple Silicon. The re-deferral's trigger ("first Apple Silicon
  machine or first >1 GiB loop budget") is unaffected.
- Adapter selection must prefer the discrete GPU explicitly on a dual-GPU
  machine (wgpu power preference) — otherwise decode and render can land on
  the Intel iGPU and the AMD card sits idle. One line, load-bearing.
- The format ladder is now load-bearing, not cosmetic: one 10-second RGBA8
  loop is 2,373 MiB against this machine's ceiling, so NV12-vs-RGBA8
  selection ([RI-2]'s resource model) decides what shows are legal here.
- **The mission test:** the dress rehearsal and the 30-minute AC-5 soak,
  green on the Intel machine, are the proof the project exists to produce.
  That run is a release gate, not a curiosity.

## 5. The `sequenceRef` decision — executed

The review ran the pre-defined procedure: zero references to `sequenceRef` in
any P1–P6 manifest, fixture, or wire log, and no 07–13 upgrade pass named a
requirement the flat rundown cannot express. **Recommendation: retire.**
v0.4 deletes the reserved hook (`Item.kind`, `sequence.arm`), which is the
full extent of the schema touch — hook removal, no registry.

## 6. Prompt-map notes (from the pause discussions)

- **08 (Companion mapping), elevated to normative requirement.** The input
  surface is device-agnostic by requirement, not courtesy. The §16 command
  surface with token auth and audit is already the device-independent core.
  08 builds a **mapping layer that is data, not code**: an **Input Intent**
  schema mapping physical intents (Companion button, MIDI note, keyboard
  chord) to semantic §16 commands, with per-device profiles as user-editable
  documents. The Input Intent schema is a wire-level contract and receives
  normative spec text at 08's moment (in v0.4 if it is the open revision, or
  a patch release otherwise). The proof of generality is normative, not
  aspirational: a keyboard-shortcut adapter ships in the same prompt, and the
  test is that the second adapter works with zero changes to the core.
  Target hardware: StreamDeck XL via Companion.
- **Naming:** if NBE becomes ONBE for the open-source era, that is a
  vocabulary event — it enters `VOCABULARY.md` with the revision that adopts
  it, not before. No code churn ahead of that.
- **Portability stance:** superseded by §0 — the primary target is the Intel
  Mac; `docs/portability.md` ([RI-7]) still enumerates the boundaries, now
  with the Apple Silicon direction recorded as the future port.
